My First Test Method

The fastest way to understand what C#RA actually buys you is to look at the same test, written twice: once the old way, calling the IG-XL API directly, and once the new way, built on TheLib.

Both versions below are real, shipped code — Continuity.Parallel, a continuity/short check that forces current on a pin list and checks the resulting voltage. You have both files, at ReferenceLibraries/CsTestMethods/Continuity/Parametric.cs and ReferenceLibraries/CsraTestMethods/Continuity/Parametric.cs.

The Old Way — CsTestMethods

This is a raw C# test method. Every hardware action is a direct call into the IG-XL object model (TheHdw), and there's no separation between validation, setup, measurement, and cleanup — it's all one block.

using Teradyne.Igxl.Interfaces.Public;
using static Teradyne.Igxl.Interfaces.Public.Constants.Global_Units;

namespace CsTestMethods.Continuity {

    [TestClass]
    public class Parametric : TestCodeBase {

        [TestMethod]
        public void Parallel(PinList pinList, double current, double clampVoltage, double waitTime) {

            TheHdw.Digital.ApplyLevelsTiming(true, true, true, tlRelayMode.Powered);
            TheHdw.Digital.Pins(pinList).Disconnect();
            var ppmu = TheHdw.PPMU.Pins(pinList);
            ppmu.Connect();

            ppmu.ForceI(current, current);
            if (current >= 0) {
                ppmu.ClampVHi.Value = clampVoltage > ppmu.ClampVHi.Max ? ppmu.ClampVHi.Max : clampVoltage;
                ppmu.ClampVLo.Value = ppmu.ClampVLo.Min;
            } else {
                ppmu.ClampVHi.Value = ppmu.ClampVHi.Max;
                ppmu.ClampVLo.Value = clampVoltage < ppmu.ClampVLo.Min ? ppmu.ClampVLo.Min : clampVoltage;
            }
            ppmu.Gate = tlOnOff.On;
            TheHdw.SetSettlingTimer(waitTime);
            var meas = ppmu.Read(tlPPMUReadWhat.Measurements, 1, tlPPMUReadingFormat.Average).ToPinSite<double>();

            ppmu.Gate = tlOnOff.Off;
            ppmu.Disconnect();
            TheHdw.Digital.Pins(pinList).Connect();
            TheExec.Flow.TestLimit(ResultVal: meas, ForceVal: current, ForceUnit: UnitType.Custom, CustomForceunit: "A",
                ForceResults: tlLimitForceResults.Flow);
        }
    }
}

A few things to notice, because they're the pain points C#RA was built to remove:

  • Everything runs in a single pass. There's no validation step — a bad pin name or an out-of-range wait time only surfaces when the flow actually tries to run on the tester.
  • Clamp logic is hand-rolled inline (current >= 0 ? ... : ...), and this exact block is duplicated wherever a similar test is written — see Serial right below it in the same file.
  • The pass/fail decision is pushed all the way down to a raw TheExec.Flow.TestLimit(...) call with a hardcoded "A" unit string.
  • Nothing here is reusable across instrument types. If this pin list happened to be DCVI or DCVS pins instead of PPMU, this code would need a different implementation.

The New Way — CsraTestMethods

Same test, same behavior, built on TheLib and following the four-phase pattern.

using System;
using Csra;
using Teradyne.Igxl.Interfaces.Public;
using static Csra.Api;

namespace CsraTestMethods.Continuity {

    [TestClass(Creation.TestInstance), Serializable]
    public class Parametric : TestCodeBase {

        private Pins _pins;
        private PinSite<double> _meas;
        private bool _containsDigitalPins = false;

        [TestMethod, Steppable, CustomValidation]
        public void Parallel(PinList pinList, double current, double clampVoltage, double voltageRange, double waitTime, string setup = "") {

            if (TheExec.Flow.IsValidating) {
                TheLib.Validate.Pins(pinList, nameof(pinList), out _pins);
                TheLib.Validate.InRange(waitTime, 0, 600, nameof(waitTime));
                _containsDigitalPins = _pins.ContainsFeature(InstrumentFeature.Digital);
            }

            if (ShouldRunPreBody) {
                TheLib.Setup.LevelsAndTiming.Apply(true);
                Services.Setup.Apply(setup);
                if (_containsDigitalPins) TheLib.Setup.Digital.Disconnect(_pins);
                TheLib.Setup.Dc.Connect(_pins);
            }

            if (ShouldRunBody) {
                TheLib.Setup.Dc.SetForceAndMeter(_pins, DcOutputMode.ForceCurrent, current, current, clampVoltage, DcMeterMode.Voltage, voltageRange);
                TheLib.Execute.Wait(waitTime);
                _meas = TheLib.Acquire.Dc.Measure(_pins);
            }

            if (ShouldRunPostBody) {
                TheLib.Setup.Dc.Disconnect(_pins);
                if (_containsDigitalPins) TheLib.Setup.Digital.Connect(_pins);
                TheLib.Datalog.TestParametric(_meas, current, "A");
            }
        }
    }
}
Note

Before reading the comparison: the attributes are not the difference. [TestClass(Creation.TestInstance)], [Serializable], [TestMethod] and [Steppable] are all IG-XL attributes, available to either style — the old-way sample above simply doesn't use them. The only C#RA addition is [CustomValidation]. What actually changes is the body of the method.

What Changed, and Why

Old (CsTestMethods) New (CsraTestMethods) Why it matters
No validation phase if (TheExec.Flow.IsValidating) calls TheLib.Validate.Pins / InRange Bad pin names or out-of-range arguments are caught at flow load, before any silicon is touched
Hand-rolled clamp logic per test TheLib.Setup.Dc.SetForceAndMeter(...) Clamp/force/meter setup is centralized in one block, so it's fixed once for every test that uses it, not once per copy-paste
Direct TheHdw.PPMU / TheHdw.Digital calls TheLib.Setup.Dc / TheLib.Setup.Digital TheLib routes to the correct instrument type (PPMU, DCVI, DCVS) automatically — the test method doesn't need to know which hardware is behind the pin
Raw TheExec.Flow.TestLimit(...) with a literal unit string TheLib.Datalog.TestParametric(_meas, current, "A") One consistent datalog call shape across all test methods, including automatic offline midway-pass handling
One undivided method body Validate → PreBody → Body → PostBody Each phase has a single responsibility, and ShouldRunPreBody / ShouldRunBody / ShouldRunPostBody let IG-XL's stepping/debug tools run just one phase at a time
Everything inline, nothing survives between phases State (_pins, _meas, _containsDigitalPins) held in private fields Work done once in Validate (like checking pin type) doesn't need to be redone in every phase

Note the new version takes two more parameters than the old one: a required voltageRange and an optional setup.

voltageRange is not a rewrite artifact — TheLib.Setup.Dc.SetForceAndMeter needs an explicit meter range, where the old code left the PPMU's range at whatever it was last configured to. It's a small example of a pattern you'll see elsewhere in C#RA: the framework version is sometimes slightly more explicit about hardware state than the raw API version, because it's designed to be correct by default rather than correct by convention.

setup is the hook into the Setup Service — pass the name of a named setup and it is applied during PreBody, so hardware configuration can be declared once and reused across test methods instead of being hard-coded here. Leaving it empty skips that step.

Note

[CustomValidation] is what enables the TheExec.Flow.IsValidating block to run at flow load time. The other attributes are IG-XL's, as noted above.

Try It Yourself

  1. Run Demo/generate-subset-solution.cmd to produce SOC124.sln, which contains every shipped project. Open it and you have both test method libraries in one place.
  2. Open the two Parametric.cs files side by side, from ReferenceLibraries/CsTestMethods/Continuity/ and ReferenceLibraries/CsraTestMethods/Continuity/.
  3. Find the Serial method in each file — it's the same comparison, one level up in complexity (it loops per-pin instead of measuring all pins at once).
  4. Run the demo. Demo/_LoadProgram.cmd starts IG-XL against the sample program, so you can step through a C#RA test method end to end — see Download & Extract.
  5. Skim TheLib Pipeline to see the full set of Setup / Execute / Acquire / Datalog methods available beyond what this one test method uses.
