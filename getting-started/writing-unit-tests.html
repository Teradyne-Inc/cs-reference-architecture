Unit Testing Your Test Methods

Not the device tests that screen silicon — this page is about proving the C# logic inside your test methods is correct before it ever reaches hardware. Unit tests are the first of three tiers (unit, offline integration, online integration) and the cheapest place to catch a defect; see Unit & Integration Testing for how the three fit together.

C#RA test methods run through the .NET Test Harness for IG-XL, which mocks TheHdw and TheExec so your tests run without a physical tester or IG-XL installed. Instead of measuring real hardware, a unit test verifies that your test method made the right calls with the right arguments — connect the right pins, force the right value, log the right result.

Note

From IG-XL 11.00.08 onwards the .NET Test Harness is delivered as part of IG-XL itself, so no separate installation is required.

What You Get

The release package ships a ready-to-use example project:

Item Path in the package What it is
UnitTestExample project ReferenceLibraries/UnitTests/UnitTestExample.csproj A working MSTest project you can copy into your own solution as a starting point
Base ReferenceLibraries/UnitTests/Base.cs The base class you inherit. Sets up the mocks and gives you the pin/pattern faking helpers
Example_UT ReferenceLibraries/UnitTests/Example_UT.cs Nine worked examples, one per testing technique — copy the shape you need

Copy this project, point it at your own test methods, and inherit Base. You do not need to reproduce any of the harness plumbing yourself.

Note

UnitTestExample.csproj references ..\..\Core\Csra\Csra.csproj, so keep the Core and ReferenceLibraries folders in the same relative arrangement they have in the package.

Anatomy of a Test Class

Inherit Base and you get three mocks, already wired up and reset before every test:

[MsTest.TestClass]
public class MyTests_UT : Base {
    // _mockTheHdw, _mockTheExec and _mockTheProgram are ready to use
}

Base handles the setup for you — for reference, this is what it does in [TestInitialize]:

protected Mock<IHdwL> _mockTheHdw;
protected Mock<IExecL> _mockTheExec;
protected Mock<IProgramL> _mockTheProgram;

[MsTest.TestInitialize]
public void TestInit() {
    _mockTheHdw = new Mock<IHdwL>() { DefaultValue = DefaultValue.Mock };
    _mockTheExec = new Mock<IExecL>() { DefaultValue = DefaultValue.Mock };
    _mockTheProgram = new Mock<IProgramL>() { DefaultValue = DefaultValue.Mock };

    Api.Services.Alert.Reset();
    Api.Services.Setup.Reset();
    Api.Services.Storage.Reset();
    Api.Services.Behavior.Reset();
    PinsFactory.Reset();

    TestHarness.SiteCount = 2;
    TestHarness.SetupTestHarnessMoq(_mockTheHdw, _mockTheExec, null, null, _mockTheProgram);

    Api.Configure();
}

Every service is reset between tests, so state left behind by one test cannot leak into the next.

Writing Your First Test

The common patterns, all taken from Example_UT.cs:

1. Verify a hardware method was called (Process_ForceV_VerifyMethodCall):

[MsTest.TestMethod]
public void Process_ForceV_VerifyMethodCall() {
    // Arrange
    string pinName = "PORTB";
    CreateFakePins([pinName], [InstrumentType.UP2200], _mockTheHdw, _mockTheExec);
    double voltageToSet = 3.3;
    // Act
    TheLib.Setup.Dc.ForceV(new Pins(pinName), voltageToSet);
    // Assert
    _mockTheHdw.Verify(hdw => hdw.PPMU.Pins(pinName).ForceV(voltageToSet), Times.Once);
}

2. Verify a property was set (Process_ForceV_PropertyWasSet) — note the same ForceV call routes to DCVI instead of PPMU purely because the fake pin is a UVI264:

CreateFakePins([pinName], [InstrumentType.UVI264], _mockTheHdw, _mockTheExec);
TheLib.Setup.Dc.ForceV(new Pins(pinName), voltageToSet);

_mockTheHdw.VerifySet(hdw => hdw.DCVI.Pins(pinName).Voltage.Value = voltageToSet, Times.Once);

3. Set up a return value (Process_ReadFromDependency_SetupReturnValue):

PinSite<double> returnValue = new(pinName, 3.3);
_mockTheHdw.Setup(hdw => hdw.DCVI.Pins(pinName).Meter.Read(
        It.IsAny<tlStrobeOption>(), It.IsAny<int>(), It.IsAny<double>(), It.IsAny<tlDCVIMeterReadingFormat>()))
    .Returns(returnValue.ToPinListData());

PinSite<double> actualValue = TheLib.Acquire.Dc.Measure(new Pins(pinName), DcMeterMode.Voltage);

MsTest.Assert.AreEqual(returnValue, actualValue);

4. Assert something did not happen (Process_ValidInput_TimesNever) — the blueprint for "no error was raised":

Mock<IAlertService> mockAlertService = new() { DefaultValue = DefaultValue.Mock };
Services.Configure(mockAlertService.Object);

TheLib.Validate.InRange(7, 5, 10, "");   // in range, so no error expected

mockAlertService.Verify(alert => alert.Error(
    It.IsAny<string>(), It.IsAny<int>(), It.IsAny<string>()), Times.Never);

Example_UT.cs also covers parametrized tests ([DataTestMethod] / [DataRow]), expected exceptions, site-generic types (Site<int>), and routing alert messages to Trace with a Moq Callback.

Faking Pins and Patterns

Testing a test method almost always needs a Pins object backed by a specific instrument type. CreateFakePins — on Base — wires the mocks so a real Pins resolves against a fake instrument:

// Explicit arrays
var pins = CreateFakePins(["pinA", "pinDig"], [InstrumentType.UVS256, InstrumentType.UP2200], _mockTheHdw, _mockTheExec);

// Or the comma-separated string form
var pins = CreateFakePins("pinA, pinDig", "UVS256, UP2200", _mockTheHdw, _mockTheExec);

Base also provides CreateFakePatternInfo, FakeDecomposePinList, FakeDCVIType and FakeDCVSType for the same purpose on patterns and DC instrument types.

Mocking Services and TheLib Itself

Two more mocking points exist beyond TheHdw/TheExec:

// Mock a Service
Mock<IAlertService> alertService = new Mock<IAlertService>() { DefaultValue = DefaultValue.Mock };
Services.Configure(alert: alertService.Object);

// Mock TheLib itself
Mock<ILib> mockTheLib = new Mock<ILib>() { DefaultValue = DefaultValue.Mock };
Configure(mockTheLib.Object);
Caution

Mocking ILib replaces every TheLib branch with a fake — nothing your test method calls through TheLib actually executes. That's the right tool for asserting "my test method called TheLib.Execute.Wait with the right timeout", but it's the wrong tool for asserting the test method's math or measurement logic is correct, because none of that logic runs. When you need to verify real behavior — not just that a call happened — let the real TheLib execute against the mocked TheHdw/TheExec instead of swapping TheLib out.

Running Tests and Coverage

Your copied project runs like any other MSTest project — from the Visual Studio Test Explorer, or with dotnet test / vstest.console. That is all you need for your own tests.

Alongside line coverage, two metrics are worth watching in your own test methods:

  • Cyclomatic complexity — the number of independent paths through a method. Above ~10, consider splitting it up; it's a sign the method is getting harder to test and maintain.
  • CRAP score ("Change Risk Anti-Patterns") — combines coverage and complexity to flag code that's risky to change. High CRAP means "complex and undertested" — either add tests or simplify.

Hit a Test Harness Limitation?

The Test Harness is still under active development, and you may find a hardware call it does not support yet. When that happens, leave a TODO comment in your test so the next person knows why something is skipped or commented out:

//_mockTheHdw.VerifySet(hdw => hdw.DCVI.Pins(pinsArray[1]).Gate = tlDCVGate.GateOn, Times.Once); // TODO Test Harness gap

Then raise it with the C#RA team so the gap can be tracked and closed.
