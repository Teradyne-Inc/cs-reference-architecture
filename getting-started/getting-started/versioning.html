Versioning Guide for Consumers

This page explains the C#RA versioning model and gives you all the information you need to safely consume, update, and plan migrations for C#RA in your test programs.

Quick reference: See VERSIONING.md at the repository root for a one-page summary.
Breaking-change details: See MIGRATION.md at the repository root for step-by-step migration instructions.

The Golden Rules

Follow these rules to avoid version-related build failures:

  1. Pin your C#RA copy to a named version tag — never reference HEAD or main. The tip of main is a work-in-progress, not a stable release.
  2. Never ignore [Obsolete] compiler warnings — they are migration deadlines, not suggestions. Each warning tells you exactly which version will remove the API and what the replacement is.
  3. Plan a migration sprint when a new MAJOR version is announced — do not wait until the old version reaches End-of-Life.
  4. Check CHANGELOG.md and MIGRATION.md before every update — even MINOR bumps can expose new, better patterns.
  5. Migrate off End-of-Life (EOL) versions promptly — EOL versions receive no patches or security fixes.

How to Read a Version Number

C#RA uses Semantic Versioning 2.0 (MAJOR.MINOR.PATCH):

  1  .  2  .  3
  │     │     └── PATCH — Bug fixes only. No API changes.
  │     └──────── MINOR — New features. Existing API unchanged.
  └────────────── MAJOR — Breaking changes. Migration required.

What each increment means for a Test Engineer

Bump Meaning Action required
PATCH (x.x.N+1) A bug was fixed. No public API was added or removed. ✅ Update immediately — no code changes needed.
MINOR (x.N+1.0) New capabilities were added. Nothing was removed. ✅ Update at your next opportunity. Check CHANGELOG.md for new features.
MAJOR (N+1.0.0) At least one public API was removed or changed. ⚠️ Plan a migration sprint. Read MIGRATION.md before updating.

Support Window

C#RA maintains a rolling two-MAJOR-version support window:

Version Status
Current MAJOR (N) ✅ Fully supported — receives PATCH and MINOR updates
Previous MAJOR (N-1) ⚠️ Limited support — critical patches only
N-2 and older ❌ End-of-Life — no further updates of any kind

When a new MAJOR version is released, the N-2 version is immediately EOL. Plan your migration before the next MAJOR drop so you are never left on an unsupported version.

Deprecation Timeline

APIs are never removed without advance warning:

Stage Version type What you see What to do
Deprecation warning MINOR release Compiler warning: [Obsolete("Use XYZ instead. Will be removed in vN+1.", error: false)] Migrate to the replacement at your next opportunity
Deprecation error Next MAJOR release candidate (RC) Compiler error: [Obsolete("...", error: true)] Migrate now — this MAJOR release will not compile otherwise
Removal MAJOR release API no longer exists Must be migrated to the replacement

The deprecation window is at least 2 weeks and no more than 13 weeks (one quarter) before removal.

How to Add C#RA to a New Test Program

C#RA is distributed as a source code package (zip download from GitHub Releases or eKnowledge). Reference it by copying the Csra folder next to your solution.

Step-by-step

  1. Download the release package from GitHub Releases or eKnowledge. Choose a specific tagged version (e.g., v1.2.3).

  2. Extract and copy the Csra folder from the downloaded zip to a location next to your solution file:

    MyTestProgram/
├── MyTestProgram.sln
├── MyTestProgram/
└── Csra/          ← Place here

  3. Add the project reference in Visual Studio:

    • Right-click the solution → Add > Existing Project...
    • Navigate to the Csra folder and select Csra.csproj
    • Click OK

  4. Record the version you added. Create or update a comment in your solution's README.md:

    ## Dependencies
- C#RA v1.2.3 — downloaded from GitHub Releases tag `v1.2.3`

  5. Commit everything, including the Csra folder, to your test program's source control. This ensures your program always builds against the exact version you tested.

Tip

Always record the exact version tag in your solution's documentation. When you later need to update, you will know exactly what you are upgrading from.

How to Update to a New C#RA Version

Pre-update checklist

  • [ ] Identify the version of C#RA currently in your test program (check your README.md or the AssemblyInfo.cs in the Csra folder).
  • [ ] Determine the version you want to update to.
  • [ ] Read the CHANGELOG.md entries for all versions between your current version and the target version.
  • [ ] If the target version is a MAJOR bump, read MIGRATION.md before proceeding.
  • [ ] Resolve all existing [Obsolete] compiler warnings in your code before updating. Clearing warnings now prevents them from becoming errors after the update.

Update steps

  1. Download the new release package from GitHub Releases for the target version tag.

  2. Replace the Csra folder in your test program:

    • Delete the existing Csra folder.
    • Copy the new Csra folder from the downloaded package.

  3. Rebuild your test program in Visual Studio.

  4. Address any compiler output:

    • Compiler warnings ([Obsolete(error: false)]): Note these for future migration but they will not block your build.
    • Compiler errors ([Obsolete(error: true)] or removed APIs): These must be resolved before the build succeeds. Refer to MIGRATION.md for the replacement code.

  5. Run your test program's validation suite to confirm correct behavior.

  6. Update your version record in your solution's documentation.

  7. Commit the updated Csra folder and documentation changes to your source control.

Frequently Asked Questions

Can I stay on my current version indefinitely?

No. C#RA maintains a rolling two-MAJOR-version support window. When a second new MAJOR version is released, your version becomes End-of-Life. EOL versions receive no patches, bug fixes, or security updates. If a critical issue is found in an EOL version, the fix is only available in supported versions.

Plan a migration sprint before each MAJOR release to avoid being left on an unsupported version.

What happens if I ignore [Obsolete] warnings?

Compiler warnings are your advance notice. In the release candidate (RC) of the next MAJOR version, the deprecated API's error flag is set to true, turning warnings into build errors. If you have not migrated by then, your test program will fail to compile after updating. The safest approach is to resolve [Obsolete] warnings before they become errors.

How much work is a MAJOR migration typically?

It depends on the scope of the breaking changes. MIGRATION.md enumerates every breaking change with before/after code examples. For a well-maintained test program that has been keeping up with [Obsolete] warnings, a MAJOR migration is typically a few hours of search-and-replace work. For programs that have ignored multiple cycles of deprecation warnings, it can take longer. The recommended approach is to address [Obsolete] warnings continuously so that no MAJOR migration is a large surprise.

Who do I contact if the migration guide doesn't cover my use case?

Open a GitHub Issue with the label migration-help. The C#RA team will respond and, if the gap is a real omission, update MIGRATION.md to cover the case.

Can I use two different versions of C#RA in the same test program?

No. C#RA is referenced as a single project within a solution. Version indirection (e.g., using Csra_v1; alongside using Csra_v2;) is not supported. Each test program uses exactly one version of C#RA. If you need new capabilities from a MINOR or MAJOR update, update the entire program to the new version.
