Versioning & Backwards Compatibility

Compatibility is a sensitive topic for libraries that are widely used. The cost and effort to handle incompatible updates quickly scale with broad adoption, hence compatibility requirements need to be managed well.

C#RA uses Semantic Versioning 2.0.0 (MAJOR.MINOR.PATCH) to give every consumer a clear, machine-readable signal about what changed in a release and what action — if any — is required on their part.

Compatibility Philosophy

C#RA aims to minimize breaking changes while maintaining the flexibility to improve the library when necessary. The approach balances stability for existing users with the ability to deliver better solutions for new and evolving requirements.

Version Number Model

C#RA uses a three-part MAJOR.MINOR.PATCH version scheme:

Part Incremented when… API impact
PATCH A bug is fixed with no public API change None — safe to update immediately
MINOR New capabilities are added; nothing is removed or changed Additive only — safe to update
MAJOR A public API is removed, renamed, or its signature changed Breaking — migration required

Examples of PATCH changes

  • Fix a calculation error inside an existing Test Block
  • Correct a hardware timing constant
  • Fix a null-reference exception in an edge case
  • Any change to private/internal code that does not affect the public surface

Examples of MINOR changes

  • Add a new Test Block class
  • Add an optional parameter with a default value to an existing method
  • Add a new overload for an existing method
  • Add a new service or service method
  • Mark an existing API as [Obsolete(error: false)] (deprecation warning)

Examples of MAJOR changes

  • Remove a public method, class, or interface
  • Rename a public method, class, namespace, or assembly
  • Change a method parameter (type, name, order, or optionality)
  • Promote a deprecated API from [Obsolete(error: false)] to removal
  • Restructure the service interface hierarchy

Rolling Support Window

C#RA maintains a rolling two-MAJOR-version support window:

Current MAJOR (N)     → Fully supported: receives PATCH and MINOR updates
Previous MAJOR (N-1)  → Limited: critical patches and security fixes only
N-2 and older         → End-of-Life (EOL): no further updates

When a new MAJOR version is released:

  1. The N-1 version enters limited maintenance mode.
  2. The N-2 version is immediately End-of-Life (EOL). No further updates — including patches — will be issued.
  3. EOL is communicated to consumers via GitHub Discussions, Teams, and the release notes.

This policy bounds the maintenance burden on the C#RA team to at most two MAJOR versions at any time, while giving consumers at least one full MAJOR lifecycle to plan and execute their migration.

Deprecation Process

APIs are never removed without a structured advance-notice period. The deprecation lifecycle is:

  1. Deprecation warning (MINOR release)
    The API is marked [Obsolete("Use XYZ instead. Will be removed in vN+1.", error: false)].
    Consumers see a compiler warning. This is the migration notice.
    The deprecation window lasts at least 2 weeks and no more than 13 weeks (one quarter).

  2. Deprecation escalation (next MAJOR release candidate)
    The API is marked [Obsolete("...", error: true)].
    Consumer builds that still use the deprecated API will now fail to compile.
    This forces consumer awareness before the breaking release ships.

  3. Removal (MAJOR release)
    The API is removed from the codebase.

Every deprecated API is documented in MIGRATION.md (repository root) with:

  • What was deprecated and why
  • The replacement API
  • Before/after code examples
  • The exact version it will be removed in

Compatible Changes

The following types of changes are considered compatible and can be made in MINOR or PATCH version updates:

  • Bug fixes that correct unintended behavior without affecting the public API signature
  • New Test Blocks, Test Methods, or Services added to the library
  • New overloads for existing methods
  • New optional parameters with sensible defaults on existing methods
  • Performance improvements with no observable behavior change
  • Documentation improvements or XML doc comment additions

Incompatible Changes

The following types of changes result in a new MAJOR version. They are only introduced when the benefits clearly outweigh the migration effort:

  • Removing a public class, method, property, or interface
  • Changing a method's parameter list (type, name, order, adding required parameters)
  • Changing a method's return type
  • Moving a type to a different namespace
  • Restructuring the API entry point (e.g., adding or removing a required node in the call chain)

Development Model

Development always targets the latest version of C#RA. There are no separate release branches, and features or fixes are not back-ported to previous releases (except critical patches for the N-1 version under limited maintenance).

This approach keeps the development effort focused and avoids the complexity of maintaining multiple active versions. Because C#RA is distributed as source code, test programs embed a specific version and continue to work unchanged until they deliberately upgrade.

Impact on Test Programs

Version Independence

Each test program includes a specific version of C#RA, typically the latest available when the project starts. Test programs operate independently with their own copy of the library.

There is no global installation of C#RA that affects multiple test programs. Different test programs can use different C#RA versions without conflict.

Update Strategy

Released test programs do not require C#RA updates as long as they function correctly. Updates are appropriate when:

  • The test program needs modification for other reasons (a natural migration opportunity)
  • New C#RA features would provide significant value
  • Bug fixes in C#RA address issues affecting the test program
  • The current version is approaching End-of-Life

The MAJOR version update is deliberate and controlled by the test program team. Only the specific test program being updated is affected.

Migration Effort

When upgrading to a MAJOR version:

  • Work through the MIGRATION.md section for that MAJOR version
  • The PATCH version means patch-level updates never require code changes
  • The MINOR version means feature additions never require removing existing code
  • The deprecation warning period means breaking removals are signalled well in advance

See the Versioning Guide for Consumers for step-by-step update instructions.
