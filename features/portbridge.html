PortBridge – Enable & Use

PortBridge is a Teradyne product that provides a device-communication abstraction layer for IG-XL test programs. It lets a test program talk to a device through named registers and fields (with bit-bashing, ProtocolAware and PatternModify handled underneath) instead of hand-crafted source/capture patterns.

PortBridge is an optional, separately licensed product. C#RA is built so the source tree still builds and runs on a machine without PortBridge — the PortBridge-specific projects compile to empty assemblies rather than failing the build. Only code that actually calls into PortBridge (anything referencing PBLib) requires the product to be installed to compile. 1. Prerequisites

Requirement Detail

PBROOT environment variable Set by the PortBridge install; must point at the folder containing the DLL
Valid PortBridge license Required

That's the whole "enable" step: install PortBridge and make sure PBROOT is set. There is no flag to flip in C#RA, no marker file, and no project setting — PBROOT alone decides, as section 2 describes.

2. How enabling works (auto-detection)

C#RA detects PortBridge purely from PBROOT + the presence of the DLL. No marker file is needed.

Important

A previous version relied on a manual PortBridgeEnabled.txt marker file in src. That is gone — detection is now automatic via PBROOT.

There are three coordinated pieces, all keyed on Exists('$(PBROOT)\Teradyne.PortBridge.dll'):

a) Core project — Core/Csra/Csra.csproj defines a named property and a compiler constant:

<PropertyGroup>
  <!-- true only if the DLL is found under PBROOT -->
  <PortBridgeEnabled Condition="Exists('$(PBROOT)\Teradyne.PortBridge.dll')">true</PortBridgeEnabled>
</PropertyGroup>
<PropertyGroup>
  <PortBridgeEnabled Condition=" '$(PortBridgeEnabled)' == '' ">false</PortBridgeEnabled>
</PropertyGroup>
<PropertyGroup Condition=" '$(PortBridgeEnabled)' == 'true' ">
  <DefineConstants>$(DefineConstants);PORTBRIDGE_ENABLED</DefineConstants>
</PropertyGroup>
<ItemGroup Condition=" '$(PortBridgeEnabled)' == 'true' ">
  <Reference Include="Teradyne.PortBridge">
    <HintPath>$(PBROOT)\Teradyne.PortBridge.dll</HintPath>
    <Private>False</Private>
  </Reference>
</ItemGroup>
  • PortBridgeEnabled — the MSBuild switch (auto-detected, defaults to false).
  • PORTBRIDGE_ENABLED — a compiler constant defined by the core projects that opt in (Csra.csproj, Tol.csproj, and the unit-test projects). It is not defined by the PortBridge reference projects (PortBridgeUtils.csproj, Demo_PB.csproj) — those gate their source with <Compile Include> conditions instead (see (b) below). No shipped .cs file uses an #if PORTBRIDGE_ENABLED guard today.

b) Reference libraries — the two PortBridge example projects gate both their compile items and the DLL reference directly on the same Exists(...) condition (see PortBridgeUtils.csproj and Demo_PB.csproj):

<ItemGroup Condition="Exists('$(PBROOT)\Teradyne.PortBridge.dll')">
  <Compile Include="PBLib.cs" />
  <!-- ... -->
</ItemGroup>
<ItemGroup Condition="Exists('$(PBROOT)\Teradyne.PortBridge.dll')">
  <Reference Include="Teradyne.PortBridge">
    <HintPath>$(PBROOT)\Teradyne.PortBridge.dll</HintPath>
  </Reference>
</ItemGroup>

Because every <Compile Include> is gated this way — Properties\AssemblyInfo.cs included — a machine without PortBridge doesn't merely skip some files: PortBridgeUtils and Demo_PB build into empty assemblies, and the DLL reference isn't required, so the solution still builds. The practical consequence for you: any code that references PBLib will not compile on a machine without PortBridge. The failure mode to watch for is a mis-pointed PBROOT — the build then succeeds but produces an empty PortBridgeUtils.dll, so the break surfaces at runtime as a missing PBLib rather than as a build error. If that happens, check PBROOT first.

c) Runtime version check — IGComponentManagerParser.VerifyPbVersion reads PBROOT, finds Teradyne.PortBridge.dll, and compares its file version against the required version declared for the program. This is only exercised when PBROOT is set.

Note

The CI pipeline builds and tests the subset solution both with and without PortBridge, per IG-XL version. The non-PortBridge leg validates that the PortBridge-independent projects (Csra, Tol, CsTestMethods, CsraTestMethods, UnitTestExample) can't silently regress; it does not validate PortBridge-free variants of the PortBridge projects themselves (see Unit & Integration Testing).

PortBridgeUtils / PBLib — the wrapper API

PBLib wraps the raw PortBridge language into a small, C#RA-flavored API. It hides the RegisterMaps[…].Blocks[…].SubBlocks[…].Registers[…].Fields[…].Value navigation behind flat method calls and speaks C#RA's Site<T> / SiteLong types. It supports hierarchical register paths:

  • "CFG0" — flat register
  • "PERIPH_A.CFG0" — block . register
  • "PERIPH_A.SUBBLOCK_A.CFG0" — block . sub-block . register

Key members:

Member Purpose
PBLib.Initialize(registerMapName) Sets the active register-map name (e.g. "Demo")
GetRegValue(reg) / SetRegValue(reg, Site<int>) Read/write a whole register (site-uniform or per-site)
GetRegValuePerSite / SetRegValuePerSite Same, using SiteLong
GetFldValue(reg, fld) / SetFldValue(reg, fld, val) Read/write a named field
GetFldValuePerSite / SetFldValuePerSite Field access with SiteLong
ResetRegisterAll() / ResetRegister(reg) Restore default (reset) values
CheckLabel(reg) / CheckFieldLabel(reg, fld) Validate a register/field exists in the map
GetFieldMask(reg, fld) Get a field's bit mask
OpenInDebugTool(module) Open a module in the PortBridge Debug Tool

The static PortBridge handle it uses:

public static IPortBridgeLanguage PortBridge = new PortBridgeLanguage_Remote("IG.NET");

Demo_PB — how it's put together

Lifecycle wiring — ExecInterposeClass.cs. PortBridge is initialized when the program loads, via an Exec Interpose:

[ExecInterpose_OnProgramLoaded(255)]
public static void OnProgramLoaded() {
    Initialize.PortBridgeInit();
    Services.Alert.Log("PB initialized successfully");
}

Init & register-map load — Initialize.cs.

// Called once at program load
public static void PortBridgeInit() {
    PortBridgeLanguage portBridge = new PortBridgeLanguage();
    portBridge.Initialize(TheHdw.Tester.Type);
    portBridge.Utilities.Logger.ShowInformationEntries = true;
    portBridge.Utilities.ShowStatusMonitor();          // real-time monitor
}

// Called from the first test to load the map and build a test configuration
public static void PortBridgeSetup() {
    PBLib.Initialize("Demo");                          // active register-map name
    PBLib.PortBridge.RegisterMaps.Unload(REGISTER_MAP);
    if (!PBLib.PortBridge.RegisterMaps.Contains(REGISTER_MAP)) {
        PBLib.PortBridge.RegisterMaps.Load(
            REGISTER_MAP,                              // "Demo"
            ".\\Portbridge_Files\\demo.svd",          // the SVD map
            PortBridgeRegisterMapFormat.SVD,
            string.Empty, false, false, string.Empty, false);
        IPortBridgeTestConfiguration pb = PBLib.PortBridge.Tests.Configurations["RM1"];
        pb.RegisterMap.Add(REGISTER_MAP);              // bind map ↔ config "RM1"
    }
}

The demo device — Portbridge_Files/demo.svd. A generic CMSIS-SVD file (RegMap_Demo) with a PERIPH_A peripheral, SUBBLOCK_A cluster, CFG0 register and a SEL field — i.e. the PERIPH_A.SUBBLOCK_A.CFG0 path the tests use.

The TestMethods — PB_Tests.cs. All are [TestMethod, Steppable, CustomValidation]:

TestMethod Demonstrates
InitialSetup() Calls PortBridgeSetup(), resets registers, confirms the map loaded and the hierarchical path resolves (CheckLabel)
ReadAndLogRegister(regLimit, fldLimit) Reads register + field, tests them against limits with TheExec.Flow.TestLimit
Check_SiteGenerics() Site<int> ↔ SiteLong conversions with register/field set/get, per-site values
VerifyRegisterReadWrite() Full reset → read → write pattern → read-back → verify → restore, per site, at register and field level

4. Using it in your own program

  1. Install PortBridge and confirm PBROOT points at the folder holding Teradyne.PortBridge.dll. Rebuild — the PortBridge code now compiles in and PORTBRIDGE_ENABLED is defined.

  2. Provide your register map as an SVD (or another format PortBridge supports) and load it the way PortBridgeSetup() does — change the map name, file path and test-configuration name to yours.

  3. Initialize once from an OnProgramLoaded Exec Interpose (as ExecInterposeClass does).

  4. Call PBLib from your TestMethods using named registers/fields:

    PBLib.ResetRegisterAll();
PBLib.SetFldValue("PERIPH_A.SUBBLOCK_A.CFG0", "SEL", myTrim);   // myTrim is Site<int>
Site<int> readback = PBLib.GetRegValue("PERIPH_A.SUBBLOCK_A.CFG0");
TheExec.Flow.TestLimit(readback, lo, hi, FormatStr: "%x", TName: "CFG0");

  5. Keep PortBridge-only source out of non-PortBridge builds the way the shipped projects do — gate each <Compile Include> in the .csproj on Exists('$(PBROOT)\Teradyne.PortBridge.dll') (see §2 (b)), rather than reaching for #if PORTBRIDGE_ENABLED. That constant is defined only by the core projects (Csra/Tol/UT), not by the PortBridge reference projects — so a #if PORTBRIDGE_ENABLED added to a copied PortBridge project evaluates false and silently compiles nothing, a build that "passes" while covering zero code. If you do want #if guards, add PORTBRIDGE_ENABLED to that project's <DefineConstants> first.

5. Building

The trimmed solution (SOC124) is generated on the fly and can be built either way. Run Demo/generate-subset-solution.cmd, which adds PortBridgeUtils.csproj and Demo_PB.csproj to a classic-format .sln (forced, because these are non-SDK .NET Framework 4.8 projects), then build it in Visual Studio.

Which way it builds is decided entirely by PBROOT, as described in section 2:

  • PBROOT set and Teradyne.PortBridge.dll present — the PortBridge projects compile against the kit and PBLib is available.
  • PBROOT unset or empty — the same projects compile to empty assemblies and the build still succeeds. This is deliberate: a program that does not use PortBridge must not need the kit.
Tip

If a build appears to succeed but PBLib is missing at runtime, check PBROOT first. A mis-pointed PBROOT is the usual cause — it produces an empty PortBridgeUtils.dll rather than a build error.

Every C#RA release is validated both ways, with and without the kit, plus a negative case that confirms a missing kit fails the build rather than passing silently.

To run the full demo program, generate/load the IG-XL project with Demo/_GenerateProgram.cmd / _LoadProgram.cmd; the PortBridge subprogram and Demo_PortBridge job in Demo.igxlProj exercise the flow, and OnProgramLoaded runs PortBridgeInit() automatically.

Note

In the demo, PBLib.PortBridge is a PortBridgeLanguage_Remote("IG.NET") instance, while Initialize.PortBridgeInit() constructs a separate local new PortBridgeLanguage() for the logger/status-monitor bring-up — they are two distinct PortBridge objects.

Note

PBLib is a reference helper, not a fixed API. Extend or replace it for your device — it exists to show the pattern (hierarchical paths, Site<T>/SiteLong bridging, reset/verify flows) rather than to be an exhaustive transaction layer.
