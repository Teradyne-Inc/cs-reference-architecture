v0.20.0 - 2026-09-15

Breaking Changes

Note

Note on versioning: While C#RA is pre-1.0 (0.x), the SemVer 2.0 rule that reserves breaking changes for a MAJOR bump does not yet apply — any release may include breaking changes, and the two-stage [Obsolete] deprecation policy is waived. APIs may be removed without a prior warning release until the 1.0.0 milestone, after which the full deprecation policy takes effect.

Binary dependencies are no longer checked into the repository

The src/dep folder has been removed. It held the IG-XL test-harness assemblies for 11.00.00, 11.00.01 and 11.00.07, the PortBridge 2.70.00.0728 kit, and the Csra_Analyzer package feed. Unit test projects resolved IGXLFakes through a TestHarnessPath property that fell back to src\dep; they now resolve it from the installed kit through $(IGXLROOT), the same way the product projects always have. The Csra_Analyzer package reference, which was conditional on the in-repo feed, has been dropped. The public release package no longer ships binary dependencies.

<!-- Before -->
<TestHarnessPath Condition="'$(TestHarnessPath)' == ''">..\..\..\src\dep\$(LastSegment)</TestHarnessPath>
<HintPath>$(TestHarnessPath)\bin\IGXLFakes.dll</HintPath>

<!-- After -->
<HintPath>$(IGXLROOT)\bin\IGXLFakes.dll</HintPath>

Impact: Building or unit-testing C#RA now requires a matching IG-XL kit installed locally with $(IGXLROOT) resolving to it — there is no in-repo fallback. A machine without a kit fails immediately rather than silently building against a bundled harness (11.00.00 in CI). The Csra_Analyzer analyzer no longer runs as part of the build.

Subset solution generation now requires .NET SDK 9.0.200 or later

generate-subset-solution.cmd now passes --format sln to dotnet new sln, because .NET 10 defaults to the .slnx format, which Visual Studio 2022 before 17.12 cannot open or build (MSB4068). The script also deletes any stale SOC124.sln and SOC124.slnx before regenerating, so a leftover file from a previous run cannot be picked up.

:: Before
dotnet new sln -n SOC124 -o "." --force

:: After
dotnet new sln -n SOC124 -o "." --force --format sln

Impact: Machines that generate the subset solution need .NET SDK 9.0.200 or later; earlier SDKs do not accept --format and the command fails. No change is needed for anyone who does not run subset solution generation.

PortBridge detection no longer uses the PortBridgeEnabled.txt marker file

PortBridge is now detected uniformly through Exists('$(PBROOT)\Teradyne.PortBridge.dll') across all seven PortBridge-capable projects. v0.19.0 converted the build scripts and CI; this release converts the four projects that were still on the marker — Tol, TestMethods_UT, V1_UT and VersionAgnostic_UT. Tol had looked for the marker at src/Core/PortBridgeEnabled.txt while CI wrote src/PortBridgeEnabled.txt, so PortBridge had never actually been enabled for Tol under either scheme.

Impact: Creating or removing PortBridgeEnabled.txt no longer has any effect — set PBROOT instead. Tol now genuinely compiles with PortBridge support when the kit is installed, so PortBridge code paths that were silently disabled in that project become active for the first time.

meterVoltageRange is now rejected on every DCVS type

No DCVS instrument has a meter voltage range independent of its force range, so TheLib.Setup.Dc.Modify no longer writes Meter.VoltageRange on any DCVS type, and no longer writes Meter.CurrentRange on VS-20A, where meter and force share a single register. Both now emit a warning instead of taking the write. Validate.Dc reports the same restriction at validation time. Previously VS-5A and VS-800mA accepted the meter voltage range write.

Nothing was renamed and no signature changed: meterVoltageRange and voltageRange are two separate optional parameters that both already existed. meterVoltageRange is simply no longer honored, so callers should set the force range instead.

// Before — meterVoltageRange programmed the meter range on VS-5A and VS-800mA
TheLib.Setup.Dc.Modify(pins, meterVoltageRange: 6.0);

// After — meterVoltageRange still compiles, but warns and is ignored.
// Set voltageRange (the force range) instead; the meter follows it.
TheLib.Setup.Dc.Modify(pins, voltageRange: 6.0);

Impact: Test programs that pass meterVoltageRange for a VS-5A or VS-800mA pin now get a warning where the setting previously took effect, and the meter range follows the force range instead. Review any code that relied on an independent meter range — the measurement range may differ from what it was on v0.19.0. See MIGRATION.md for the migration note.

Bug Fixes

DCVI now accepts negative force values when the setpoint is reused as the range

Tol.DcviPins.ForceI and Tol.DcviPins.ForceV now apply Math.Abs() to range values before passing them to the hardware API. Callers commonly supply the same signed value as both the force value and the range; a negative range resolved to the wrong hardware bucket and the run failed with ERROR DCVI:0132. All four paths are covered — SetCurrentAndRange, SetVoltageAndRange, and the direct CurrentRange.Value and VoltageRange.Value assignments. DCVS is unaffected and out of scope.

// Forcing -100 uA with the same signed value used as the range
// Before: ERROR DCVI:0132
// After:  range resolves from the magnitude and the force succeeds
TheLib.Setup.Dc.SetForceAndMeter(pins, DcOutputMode.Current, -100e-6, -100e-6, ...);

Impact: Test methods that force negative current or voltage on DCVI pins no longer fail because a signed setpoint is misinterpreted as a negative range. This fix was announced in the v0.19.0 notes but merged after the v0.19.0 tag was cut, so it ships for the first time in v0.20.0 — if you are on v0.19.0, you do not have it.

UVS64HP DCVS pins no longer fail when a voltage range is constructed

Csra.Setting.TheHdw.Dcvs.Pins.VoltageRange resolved defaults for VS-800mA and VS-5A only. A UVS64HP (VS-20A) pin fell through to the default branch, raised Wrong DCVS pin type! Only support UVS64 & UVS256HP currently. and took a 0.0 V default. Because the default is resolved in the constructor, every VoltageRange on a UVS64HP pin failed at construction. VS-20A now defaults to 6.0 V.

// Before: Alert.Error("Wrong DCVS pin type!") and a 0.0 V default
// After:  constructs normally, 6.0 V default
var range = new Csra.Setting.TheHdw.Dcvs.Pins.VoltageRange(3.0, "vcc_hp");

Impact: UVS64HP pins can now be used from any test method that sets a DCVS voltage range. Previously the instrument was unusable through C#RA.

PPMU pins no longer datalog undefined measurements after an ignored SetMeter call

TheLib.Setup.Dc.SetMeter configures pins.Dcvi and pins.Dcvs only. On a PPMU pin it emitted a warning and did nothing, and the measurement that followed returned whatever the pin's residual mode produced — an undefined value datalogged against limits. The affected reference test methods now skip the call for PPMU pins and establish the measured pin's mode with ForceHiZ instead: Search.Parametric.LinearFull, Search.Parametric.LinearStop, Parametric.SingleCondition.Baseline, Parametric.SingleCondition.PreconditionPattern, and four of the five Resistance.RdsOn methods — TwoPinsOneForceOneMeasure, TwoPinsDeltaForceDeltaMeasure, ThreePinsOneForceTwoMeasure and FourPinsTwoForceTwoMeasure. Resistance.RdsOn.Baseline was already correct; it uses SetForceAndMeter. Parametric.MultiCondition.Baseline and Parametric.MultiCondition.PreconditionPattern take the same approach through the array overload, filtering PPMU groups out so the call still dispatches for the DCVI and DCVS groups.

// Before — warned, did nothing, and the measurement that followed was undefined
TheLib.Setup.Dc.SetMeter(_measurePin, DcMeterMode.Voltage, _voltageRange);

// After — the mode is established by ForceHiZ; SetMeter is skipped for PPMU
TheLib.Setup.Dc.ForceHiZ(_measurePin);
if (!_measurePin.ContainsFeature(InstrumentFeature.Ppmu)) {
    TheLib.Setup.Dc.SetMeter(_measurePin, DcMeterMode.Voltage, _voltageRange);
}

Impact: Test methods measuring on PPMU pins now datalog a defined measurement instead of a residual-mode value judged against limits. The SetMeter does not support PPMU warnings that the demo program emitted are gone because the unsupported call was removed, not silenced — if you see that warning in your own code, the measurement after it is not trustworthy.

DCVS and DCVI capture signal reads no longer throw InvalidCastException

Reading a capture signal from a DCVS or DCVI pin failed every time. The conversion assumed IG-XL returns a flat array — true for a meter array read, but for a capture signal IG-XL hands back an IDspWave COM proxy, which can only be cast to an interface. The conversion now unwraps IDspWave.Data, falls back to element-wise conversion under CultureInfo.InvariantCulture when the shape is neither, and otherwise throws naming the actual runtime type along with the pin and site. This affects Tol.DcvsPins.ReadSignal, ReadSamples and MeasureSamples, the same three methods on Tol.DcviPins, the Tol.PpmuPins sampled-measure path, and TheLib.Acquire.Dc.ReadCapturedSamples.

// Before — on every DCVS/DCVI capture signal read:
// System.InvalidCastException: Unable to cast object of type
// '...ComplexClientViewProxyForIDspWaveAndIDspWave...' to type 'System.Double[]'
PinSite<double[]> samples = TheLib.Acquire.Dc.ReadCapturedSamples(pins, signalName);

Impact: DCVS and DCVI capture signal reads return data for the first time — the path had never worked. The explicit invariant culture also matters on a tester configured with a comma decimal separator, where the previous ambient-culture conversion would have read 1.5 as 15 and datalogged it without complaint.

Capture pin lookup no longer fails on IG-XL's lower-cased pin names

Csra.Pins.ArrangePinSite indexed capture results in a case-sensitive dictionary, but IG-XL returns capture pin names lower-cased, so every lookup missed and the run failed with Pin 'V_VIKING0' not found in reference. — a message that sent users to the pin map when the real problem was a string comparison. Lookups now use StringComparer.OrdinalIgnoreCase, and each result entry is rewritten with the caller's pin-map casing. Both overloads were fixed, so this covers every TheLib.Acquire.Dc read path: Measure, MeasureSamples, ReadCaptured, ReadCapturedSamples, ReadMeasured and ReadMeasuredSamples.

Impact: Captures on pins whose pin-map casing differs from IG-XL's no longer fail with a misleading pin-map error. Two side effects worth knowing: PinName on Acquire.Dc results now consistently carries your pin-map casing rather than whatever IG-XL returned, so any code comparing PinName with an ordinal string comparison may see different values; and overlapping pin groups now resolve first-occurrence-wins instead of colliding. Together with the IDspWave fix above, this is what makes ReadCapturedSamples work — neither fix alone delivers a working capture read.

DsscCapture.ReadStv no longer returns elements that throw on access

Tol.DsscCapture.ReadStv() returned a PinSite<double[]> that looked correct — right pin and site counts, no exception at the call. ToPinSite<double[]> converts lazily, so the bad IDspWave cast surfaced only when an element was read, as a SiteInternalException whose stack pointed at the caller rather than at ReadStv. The conversion is now eager.

// Before — threw at element access, far from the cause
return CaptureSignals[_signalName].DspWave.ToPinSite<double[]>();

// After — unwraps immediately, so failures surface at the read
return CaptureSignals[_signalName].DspWave.ToPinSiteArray<double>();

Impact: DSSC STV captures return usable data instead of a structure that throws when touched, and any remaining conversion failure is reported at ReadStv with the runtime type and the pin and site named. Pins and sites with no captured data now yield an empty array rather than throwing.

Documentation site builds and publishes again

The docfx agent declared no tester software, so D4T installed no IG-XL kit, IGXLROOT was unset, and Igxl.Interfaces.Public resolved through a HintPath of null\bin\... — one MSB3245 warning followed by roughly 500 CS0246 errors. The agent now installs IG-XL 11.00.10, and resolveIgxlRoot() fails fast naming the agent and the missing kit rather than emitting a null path.

Impact: The documentation site and Docs_v<version>.zip are published again. No C#RA source changed, so consumers upgrading for this fix alone receive identical binaries.

Improvements

HRAM capture is now fully implemented behind IDigitalCapture

Tol.HramCapture was a stub in v0.19.0 — a parameterless constructor, with Pins, Reset(), ReadFails() and ReadStv() all throwing NotImplementedException. It is now fully implemented. The constructor takes the capture type, pins, capture limit and time domain, validates that the capture type is Fail or STV, and configures the capture type, size and trigger at construction time. ReadFails() returns the failing cycles per pin and site, omitting pins and sites with no failures; ReadStv() returns the captured bits. HRAM and CMEM now present the same IDigitalCapture surface, so a caller can switch capture technology without changing test method code. New reference test methods CsraTestMethods.Capture.Hram.CaptureFails and CsraTestMethods.Capture.Hram.CaptureStv demonstrate both modes, and the demo rows reuse the CMEM patterns so the two technologies can be cross-validated against each other.

HramCapture capture = new(CaptType.Fail, pins.Digital, captureLimit: -1, timeDomain);
TheLib.Execute.Digital.RunPattern(pattern);
PinSite<int[]> failCycles = capture.ReadFails();
capture.Reset();

Impact: HRAM is now a usable capture option rather than a stub. Code written against IDigitalCapture runs unchanged on either HramCapture or CmemCapture. The parameterless new HramCapture() no longer exists — use the four-argument constructor. Nothing could have depended on the old form, since every member of the stub threw.

New Tol.DcvsSlotType names the DCVS slot-type strings

DCVS slot-type literals were duplicated across five places. Tol.DcvsSlotType now holds them as constants — Uvs64 (VS-5A), Uvs256Hp (VS-800mA), Uvs64Hp (VS-20A), HexVs and Vsm — alongside All and SupportedByTol.

// Before
if (slotType == "VS-20A") { ... }

// After
if (slotType == Tol.DcvsSlotType.Uvs64Hp) { ... }

Impact: Slot-type comparisons can be written against a named constant instead of a string literal, and SupportedByTol gives a single place to ask which DCVS instruments Tol currently supports.

New LinearFullPpmuMeasure reference test method

CsraTestMethods.Search.Parametric.LinearFullPpmuMeasure performs a linear search that forces on one pin list and measures on another using PPMU, as a worked example of the supported PPMU force-and-meter pattern.

public void LinearFullPpmuMeasure(PinList forcePins, PinList measurePin, double from, double to,
    int count, double threshold, double clampCurrent, double waitTime, string setup = "")

Impact: There is now a reference implementation to copy for PPMU-based linear search, instead of adapting a DCVI-shaped test method and hitting the unsupported SetMeter path.

Offline demo suite now runs against UVS64HP through a second channel map

A second channel map, Channel Map_Offline_Uvs64Hp, resolves vcc to a different DCVS type — slot 13 (VS-5A) under Channel Map, slot 9 (VS-20A, UVS64HP) under the new one — so the same Job_CSRA exercises the whole flow against both instruments with no test edits. A vref pin was added to Pinmap and declared N/C in Channel Map, and a new Continuity_Parametric_Parallel_Dcvi test instance was added to Subflow_CSRA behind the RequiresDcvi enable word — the first use of enable words in the demo program.

Impact: The demo now covers two DCVS instrument types from one job, and the parallel DCVI continuity test runs in CI for the first time. The UVS64HP session runs on IG-XL 11.10.00 only — UVS64HP is absent from 11.00.10, where that channel map fails with PININFO0011, so a green 11.00.10 build does not imply UVS64HP coverage.

Validation matrix moved to IG-XL 11.00.10 and 11.10.00

CI now builds and tests against IG-XL 11.00.10 and 11.10.00, and the IGXL_11_10_00_uflx preprocessor symbol is registered. IG-XL 11.00.00, 11.00.07 and 11.00.08 have been removed from the matrix.

Impact: 11.10.00 is supported and validated. C#RA is no longer verified against 11.00.00, 11.00.07 or 11.00.08 — move to a covered version before upgrading.

Getting-started documentation rewritten and expanded

The getting-started section has been substantially reworked, with new pages covering key concepts, what C#RA is, a first test method, the four-phase test method pattern, writing unit tests, repository layout, TheLib, and the available test methods. Content that previously lived only in the internal newcomer guide is now in the public documentation, and the CsraTestMethods reference pages gained per-method documentation.

Impact: A new user can follow a guided path from installation to a working test method without needing the internal guide.

PortBridge enable-and-use guide added

docs/features/portbridge.md documents enabling PortBridge (install the kit, set PBROOT), the auto-detection mechanism and the PORTBRIDGE_ENABLED constant, the runtime VerifyPbVersion check, the shipped Demo_PB example, and hierarchical register and field paths.

PBLib.ResetRegisterAll();
PBLib.SetFldValue("PERIPH_A.SUBBLOCK_A.CFG0", "SEL", myTrim);
Site<int> readback = PBLib.GetRegValue("PERIPH_A.SUBBLOCK_A.CFG0");

Impact: PortBridge setup and usage are documented in one place instead of being spread across CI scripts and project files.
