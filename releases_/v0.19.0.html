Breaking Changes

Note

Note on versioning: While C#RA is pre-1.0 (0.x), the SemVer 2.0 rule that reserves breaking changes for a MAJOR bump does not yet apply — any release may include breaking changes, and the two-stage [Obsolete] deprecation policy is waived. APIs may be removed without a prior warning release until the 1.0.0 milestone, after which the full deprecation policy takes effect.

IDigitalCapture refactor and CMEM capture implementation

IDigitalCapture has been refactored for clarity and type safety. Read(), FailingCycleData, and DeviceData were removed, and configuration now happens in the constructor instead of through a public Configure() call. As part of the same change, CmemCapture is now implemented, with typed ReadFails() and ReadStv() methods plus new CaptureFails and CaptureStv reference test methods.

// Before
digitalCapture.Configure();
digitalCapture.Read();
PinSite<int[]> fails = digitalCapture.FailingCycleData;
PinSite<double[]> stv = digitalCapture.DeviceData;

// After
PinSite<int[]> fails = digitalCapture.ReadFails();
PinSite<double[]> stv = digitalCapture.ReadStv();
digitalCapture.Reset();

Impact: Any code implementing or calling IDigitalCapture must be updated to use ReadFails() or ReadStv(), remove Configure() calls, and rely on constructor-time configuration.

Bug Fixes

Validation errors from OnValidationStart no longer trigger the "Mangled test instance name" dialog

The IG-ComponentManager compatibility check in OnValidationStart no longer reports through a validation path that requires a current test instance. This prevents Alert.Error from surfacing the misleading WriteTemplateArgumentError dialog during program-level validation and preserves the real ComponentManager message instead.

Impact: Validation now shows the actual compatibility problem instead of the confusing "Mangled test instance name" dialog, and Alert.Error is safe to call from program-level Exec Interpose functions.

DCVI now accepts negative force values when ranges share the same magnitude

Tol.DcviPins now applies Math.Abs() to current and voltage range values before sending them to the hardware API. This fixes failures when a negative force value was reused as the range for DCVI measurements.

Impact: Test methods that force negative current or voltage on DCVI pins no longer fail because a signed setpoint is misinterpreted as a negative range.

PortBridge is now auto-detected from PBROOT

PortBridge enablement no longer relies on a manual PortBridgeEnabled.txt marker file. Program load and build scripts, project configuration, CI, and related documentation now use PBROOT plus Teradyne.PortBridge.dll detection consistently.

Impact: Users no longer need to create or remove PortBridgeEnabled.txt; PortBridge support is enabled automatically when the installation is present.

Overlapping pin groups now resolve to distinct pins

PinsFactory.GetPins now deduplicates the resolved individual pin list after decomposing pin groups, while preserving first-occurrence order. This fixes measurement-time failures when one pin group is a subset of another.

return pins.Distinct().ToList();

Impact: Passing overlapping pin groups such as GroupBig, GroupSmall no longer produces duplicate physical pins or downstream "pins are duplicated" errors.

PPMU voltage metering now uses the correct range in SetForceAndMeter

TheLib.Setup.Dc.SetForceAndMeter previously passed measureRange into the PPMU ForceVSetMeterV path, even though that argument is a current range. The method now uses clampValue, which matches PPMU behavior and the existing workaround used in production.

pins.Ppmu?.ForceVSetMeterV(forceValue, clampValue, gateOn ? true : null);

Impact: PPMU ForceVoltage + MeterVoltage flows now select a meaningful current range instead of corrupting the measurement with a voltage value.

SetMeter now warns when used with PPMU pins

TheLib.Setup.Dc.SetMeter now emits an Alert.Warning when a pin group includes PPMU pins, because PPMU cannot configure its meter independently. The warning directs callers to SetForceAndMeter, which is the supported API for combined force-and-meter setup.

Impact: Users no longer get a silent no-op when calling SetMeter on PPMU pins; they receive a clear warning and an actionable alternative.

Improvements

Reusable DCVS profiling example added

C#RA now includes a reusable DCVS current and voltage profiling example, plus supporting documentation, so profiling flows are easier to discover and reuse from test methods.

string signal = DcvsProfileTool.CreateSignalName("VDD", tlDCVSMeterMode.Current);
DcvsProfileTool.StartProfile(pins.Dcvs, signal, tlDCVSMeterMode.Current, 1.0, 100000, 500);
TheLib.Execute.Digital.RunPattern(patternInfo[0]);
DSPWave wave = DcvsProfileTool.PlotProfile(pins.Dcvs, signal, plotWaveform: true, dumpToFile: true);

Impact: Users now have a concrete C# pattern for DCVS profiling instead of relying on ad hoc implementations or VBA-only examples.

HRAM capture construction and reset are now implemented

Tol.HramCapture now performs construction-time HRAM setup and supports Reset() for the supported Fail and Stv capture modes.

var captureFail = new HramCapture(CaptType.Fail, digitalPins, captureLimit: 100, timeDomain: "");
capture.Reset();

var captureStv = new HramCapture(CaptType.Stv, digitalPins, captureLimit: 100, timeDomain: "");
capture.Reset();

Impact: Consumers can now construct and reset HramCapture objects instead of hitting NotImplementedException.

DSSC capture support added

Added DSSC support to the capture mechanism.

Impact: Users can now use DSSC as a supported capture option within the capture framework.

IDatalog gained explicit-limit overloads and named functional logging

IDatalog.TestFunctional now accepts an optional tName, and new explicit lo and hi limit overloads were added for Site<int> and PinSite<double> in TestParametric.

Impact: Users can assign explicit test names to functional datalogs and use limit-based parametric logging consistently across more result types.
