Test methods that capture digital pattern execution data using HRAM (Hardware RAM), either failing cycle indices (CaptureFails(Pattern, PinList, int, string, string)) or raw digitized device data (CaptureStv(Pattern, PinList, int, string, string)). Both methods run the configured pattern once, read the requested data back via HramCapture, and datalog per-pin/per-site counts of the data captured (failing cycles for CaptureFails(Pattern, PinList, int, string, string), samples read for CaptureStv(Pattern, PinList, int, string, string)).

CaptureFails(Pattern, PinList, int, string, string)

Captures failing cycle indices for the configured pattern/pins using HRAM.

[TestMethod]
[Steppable]
[CustomValidation]
public void CaptureFails(Pattern pattern, PinList pinList, int captureLimit, string timeDomain = "", string setup = "")

Parameters

pattern Pattern

Pattern name to capture on.

pinList PinList

Pin list to capture on. Must resolve to digital pins — non-digital pins are validated by Csra.Api.TheLib.Validate.Pins but leave Pins.Digital null, which is only detected when the HramCapture is constructed in the body.

captureLimit int

Maximum number of cycles to store in HRAM. Must be -1 (max depth), 0 (hardware default), or a positive value; validated at validation time and, redundantly, by HramCapture itself.

timeDomain string

Optional. Digital time domain to configure. Default value is an empty string (targets the System time domain). If non-empty, must match one of the time domains associated with the resolved pattern; validated at validation time.

setup string

Optional. Setup to be applied before the pattern is run.

Remarks

Only a single resolved pattern is supported; if pattern resolves to more than one pattern, validation fails with an error and the pattern list is discarded so the body does not run.

A non-empty timeDomain is checked, at validation time, against the time domains associated with the resolved pattern (TimeDomain); a mismatch is alerted as an error during validation instead of only surfacing later as a hardware error when HramCapture is constructed in the body.

The HramCapture is constructed inside the try block, alongside running the pattern and reading data, so any exception thrown by the constructor itself (for example ArgumentNullException when Pins.Digital is null, or ArgumentOutOfRangeException for an invalid captureLimit) is caught and alerted the same as a failure running the pattern or reading captured data, via Services.Alert. The capture is always reset in a finally block; this is a no-op if construction itself failed, since capture is still null in that case.

The datalogged parametric reports, per pin/site, the number of failing cycles captured — not the cycle offsets themselves. Pins with zero failures on a site (or pins with no digital component at all) log a count of 0.

Pattern name to capture on.

Pin list to capture on. Must resolve to digital pins — non-digital pins are validated by Csra.Api.TheLib.Validate.Pins but leave Pins.Digital null, which is only detected when the HramCapture is constructed in the body.

captureLimit int

Maximum number of cycles to store in HRAM. Must be -1 (max depth), 0 (hardware default), or a positive value; validated at validation time and, redundantly, by HramCapture itself.

timeDomain string

Optional. Digital time domain to configure. Default value is an empty string (targets the System time domain). If non-empty, must match one of the time domains associated with the resolved pattern; validated at validation time.

setup string

Optional. Setup to be applied before the pattern is run.

Remarks

Only a single resolved pattern is supported; if pattern resolves to more than one pattern, validation fails with an error and the pattern list is discarded so the body does not run.

A non-empty timeDomain is checked, at validation time, against the time domains associated with the resolved pattern (TimeDomain); a mismatch is alerted as an error during validation instead of only surfacing later as a hardware error when HramCapture is constructed in the body.

The HramCapture is constructed inside the try block, alongside running the pattern and reading data, so any exception thrown by the constructor itself (for example ArgumentNullException when Pins.Digital is null, or ArgumentOutOfRangeException for an invalid captureLimit) is caught and alerted the same as a failure running the pattern or reading captured data, via Services.Alert. The capture is always reset in a finally block; this is a no-op if construction itself failed, since capture is still null in that case.

The datalogged parametric reports, per pin/site, the number of raw samples read back (each digitized value is 0, 1, or 255 for midband/undefined, per ReadStv()) — not the sample values themselves. Pins with no captured data on a site (or pins with no digital component at all) log a count of 0. Because ReadStv() reads back the maximum captured-cycle count across all active sites (to avoid truncating whichever site captured the most), this logged count is uniform across every captured pin/site — it is not each site's actual capture depth, and is not a meaningful per-site measurement on its own.
